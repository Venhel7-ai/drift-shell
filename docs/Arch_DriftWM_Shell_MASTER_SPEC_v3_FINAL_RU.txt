======================================================================
V3 — НОРМАТИВНАЯ РЕДАКЦИЯ ДЛЯ ЕЖЕДНЕВНОЙ РАБОТЫ
======================================================================

СТАТУС V3
Эта редакция исправляет главный недостаток ранних референсов: они были оптимизированы прежде всего под красивый статичный скриншот, а не под многочасовую работу программиста, администратора серверов и пользователя tiling-WM.

V3 НЕ отменяет возможность воспроизвести исходные изображения. Вместо этого вводятся два чётко разделённых режима оформления:

1. WORK — основной production-профиль. Он обязан быть максимально спокойным, быстрым и не занимать экран без необходимости.
2. REFERENCE / SHOWCASE — профиль, который максимально близко воспроизводит исходные изображения: закреплённая правая колонка, видимый dock, широкая строка поиска и более выраженное стекло.

Если пользователь не выбрал профиль явно, запускается WORK.

При конфликте между старым текстом V1/V2 и этим блоком V3 применяется V3.

======================================================================
V3.1. ГЛАВНЫЙ ПРИНЦИП
======================================================================

Оболочка должна исчезать, когда она не нужна.

Функциональность не должна доказывать своё существование постоянным присутствием на экране. Большая часть возможностей вызывается по бинду, hover-edge, search или popover.

Нормальный рабочий экран должен визуально состоять только из:
- чёрного фона со слабыми звёздами;
- компактной верхней панели;
- рабочих окон;
- кратковременных уведомлений при необходимости.

Правой колонке, dock, notification center, popover, large search, design guides и дополнительным виджетам запрещено быть постоянно видимыми в WORK, если пользователь их явно не закрепил.

V3.8. RIGHT PANEL — ТРИ СОСТОЯНИЯ
======================================================================

Вместо бинарного show/hide вводятся:

Hidden
Peek
Pinned

HIDDEN:
- surface полностью за правой границей;
- input region пуст;
- Safe Area не резервируется;
- видимых 1–8 px hotzone по умолчанию НЕТ, если управление bind-only;
- optional edge hotzone включается настройкой.

PEEK:
- панель выезжает поверх текущих окон;
- Safe Area НЕ меняется;
- окна НЕ перераскладываются;
- panel z-level выше application windows;
- закрывается по повторному bind, Escape, click outside или timeout, если autoClose=true.

PINNED:
- панель резервирует ширину;
- tiling пересчитывается;
- panel остаётся до явного unpin.

Recommended binds:
Super+R -> Hidden <-> Peek
Super+Shift+R -> Pinned <-> Hidden/previous state

Peek width:
290 px reference.
Pinned width:
290 px reference.

Peek нельзя автоматически превращать в Pinned.

В WORK default Hidden.
В REFERENCE default Pinned.

ЧАСТЬ A. ИСХОДНОЕ ФУНКЦИОНАЛЬНОЕ ТЗ
======================================================================

Необходимо создать оболочку для моей системы. Если есть вопросы по тз то задавай. Ниже — итоговое ТЗ в виде единого связного описания. Оно объединяет всю нашу концепцию: Arch Linux, driftwm, гибрид «тайлинг + бесконечный холст», Quickshell/Caelestia-подобную оболочку, Zen Browser, уведомления, серверные инструменты, полностью настраиваемый интерфейс, минималистичный экран входа и блокировки и визуальный стиль с твоих изображений. Важное техническое решение: driftwm уже подходит как основа, потому что у него есть infinite canvas, bookmarks, layer-shell, IPC, подписка на состояние, screen-pinned поверхности, фон из точек и session lock, однако требуемый тобой режим «запретить перемещение по холсту и превратить текущую область в полноценный tiling workspace, а затем одной клавишей отпустить её обратно в infinite canvas» лучше реализовать небольшим форком driftwm, а не набором внешних скриптов. Так система получится предсказуемой и не будет конфликтов между камерой, панелями, тайлингом и пользовательским вводом. ([GitHub][1])

Проект должен представлять собой собственную рабочую среду для Arch Linux, построенную поверх driftwm и ориентированную прежде всего на программирование, работу с серверами, терминалом, браузером, Docker, Git, удалёнными машинами и постоянное использование клавиатуры. Внешне вся среда должна выглядеть как единая система, а не как набор несвязанных Linux-программ. Главным визуальным принципом является максимальный минимализм. Основной фон системы — абсолютный чёрный `#000000`. Поверх него используется встроенный или собственный shader driftwm с очень редкими маленькими белыми точками. Никаких пейзажей, гор, планет, туманностей, фотографий и сложных wallpaper на рабочем столе, экране входа и экране блокировки быть не должно. Только чёрное пространство и белые точки. Сам driftwm уже поддерживает встроенный dot-grid и GLSL-фоны, поэтому этот эффект необходимо реализовать именно на уровне compositor, а не отдельным тяжёлым приложением. ([GitHub][1])

Цветовая палитра всей собственной оболочки ограничивается четырьмя логическими цветами. Чёрный является фоном и базой всех поверхностей. Белый используется для текста, границ, иконок и обычных состояний. Зелёный используется исключительно для положительного состояния: сервер онлайн, операция выполнена, тесты прошли, устройство подключено, активная служба работает. Красный используется только для ошибки, критического события, отказавшего сервера, неудачной операции или предупреждения высокой важности. Серые оттенки отдельными цветами не задаются: они получаются исключительно изменением прозрачности белого или чёрного. Например вторичный текст — белый с opacity 0,45–0,65, рамка — белый 0,10–0,20, стеклянный фон — чёрный 0,60–0,85. В настройках пользователь должен иметь возможность изменить даже эти базовые цвета, но установленный по умолчанию профиль должен строго соблюдать эту палитру. Содержимое сторонних сайтов, изображений, видео и программ насильно перекрашивать не требуется, однако для браузера и поддерживаемых приложений должен существовать дополнительный переключатель «Монохромный интерфейс», влияющий именно на chrome приложения, а не на полезное содержимое.

Главная логическая особенность системы — два режима работы driftwm: «Закреплённая область» и «Свободный холст». После входа в систему пользователь всегда находится в режиме «Закреплённая область». Для пользователя этот режим должен ощущаться почти как обычный tiling window manager. Камера driftwm привязана к конкретной прямоугольной области бесконечного canvas. Её нельзя случайно переместить за пределы текущей зоны мышью, touchpad, жестами, клавишами pan, edge-pan или другими стандартными способами driftwm. Масштаб также зафиксирован на заданном значении, по умолчанию 100 %. Все новые обычные окна должны открываться внутри текущей области и автоматически включаться в tiling-разметку. Ни одно tiled-окно в этом режиме не должно выходить за эффективные границы рабочего пространства даже частично.

Технически рабочая область не должна быть настоящим классическим workspace. Она представляет собой сохранённую область внутри infinite canvas driftwm. Для неё хранится уникальный ID, имя, координаты центра, номер быстрого слота, размер usable-area, выбранный layout, набор открытых окон, настройки панелей и дополнительные пользовательские параметры. Таким образом на бесконечном canvas существуют независимые рабочие острова. Например зона `1` может находиться в одной части canvas и называться «Разработка», зона `2` — «Серверы», зона `3` — «Учёба», зона `4` — «Браузер», зона `5` — «Общение». В верхней панели они при этом отображаются минималистично как `1 2 3 4 5 6 7 8 9`, как на макете. Driftwm уже имеет bookmarks, хранит их координаты и экспортирует активный bookmark через IPC, поэтому именно bookmarks следует использовать как низкоуровневую основу таких зон. ([GitHub][2])

Нажатие `Super+1…9` должно плавно перемещать пользователя к соответствующей зоне и автоматически переводить её в закреплённое состояние. Активный номер в верхней панели получает чуть более яркую белую рамку и слегка повышенную opacity стеклянного фона. Никаких ярких цветных заливок для активного workspace не используется. В настройках пользователь может переименовать зоны, удалить их, создать дополнительные зоны без горячего номера, выбрать координаты, назначить иконку, задать приложение автозапуска, профиль shell и индивидуальную раскладку окон.

Для перехода к настоящему driftwm используется отдельный bind, по умолчанию `Super+Shift+Space`, однако любое сочетание должно переназначаться. После первого нажатия текущая область «открепляется». На уровне fork driftwm состояние output меняется с `Anchored` на `FreeCanvas`. Tiling-окна при этом остаются физически там, где были. Их размеры и координаты не сбрасываются. Блокировка camera pan и zoom снимается. Пользователь получает нормальный бесконечный canvas driftwm и может свободно ехать по нему в любом направлении, масштабировать пространство, искать другие области и просто использовать основной принцип driftwm. Переход сопровождается очень короткой анимацией: рамки текущих tiled-окон слегка теряют контраст примерно за 150 мс, центральный индикатор workspace сверху меняется на минималистичную иконку свободного canvas либо короткое слово «Холст», после чего камера становится свободной. Никаких обучающих надписей вроде «Теперь можно перемещаться» показывать нельзя.

Повторное нажатие `Super+Shift+Space` в свободном режиме означает «закрепить текущую позицию». Backend сначала определяет, находится ли камера рядом с уже известной зоной. Если да, камера плавно выравнивается по её сохранённому центру, zoom возвращается к значению зоны и включается её tiling layout. Если поблизости зоны нет, создаётся новая. В момент нового закрепления система не должна неожиданно захватывать все окна, которые случайно попали в кадр. В настройках должна существовать политика поведения: «оставлять найденные окна свободными», «добавлять окна в раскладку автоматически» или «выбирать окна вручную». По умолчанию безопаснее использовать первый вариант. Так пользователь никогда не разрушит случайно уже существующую часть canvas.

В форк driftwm необходимо добавить явное состояние камеры для каждого output, команды IPC `anchor`, `unanchor`, `toggle-anchor`, получение текущего состояния через `state/subscribe` и возможность полностью запретить pan/zoom в Anchored-режиме без изменения `config.toml`. Нельзя строить эту механику на постоянном редактировании конфигурационного файла и `reload-config`. Конфигурация предназначена для постоянных настроек, а переключение Anchored/FreeCanvas является runtime-состоянием. Сам driftwm уже предоставляет Unix-socket IPC, команды управления камерой, окнами и bookmarks, а также постоянную подписку `subscribe`, поэтому наша система должна расширить этот механизм, а не создавать второй параллельный протокол. ([GitHub][3])

В Anchored-режиме работает собственный tiling controller. Он не должен заменять compositor целиком; driftwm остаётся ответственным за фактическое отображение, focus, Wayland и эффекты, а layout controller рассчитывает геометрию окон. Одно окно занимает практически всю рабочую область. Два окна по умолчанию располагаются 50/50 слева и справа. При трёх окнах используется master-stack: активное главное окно занимает примерно 58 % ширины слева, два остальных делят правую часть вертикально. Четыре окна могут использовать 2?2 либо master-stack. Для пяти и более система переходит к выбранной пользователем стратегии. Обязательно реализовать layouts `Master Stack`, `Grid`, `Columns`, `Rows`, `Monocle` и пользовательское дерево. Для каждой рабочей зоны layout выбирается отдельно.

Любое изменение layout должно происходить плавно. Окна не должны телепортироваться из одной геометрии в другую. На уровне driftwm необходимо анимировать позицию и размер окна compositor-side. Стандартная длительность перестройки примерно 180–240 мс с кривой `OutCubic` либо мягкой spring-анимацией. При появлении нового окна существующие окна плавно освобождают место, новое окно появляется с opacity от 0 до 1 и scale примерно от 0,97 до 1. При закрытии происходит обратная анимация, а оставшиеся окна сразу, но плавно заполняют освободившееся место.

Пользователь должен иметь возможность менять tiled-позиции мышью. В Anchored-режиме обычный drag окна не должен превращать его в произвольное floating-окно. Вместо этого при перетаскивании поверх других tiles появляются тонкие белые зоны вставки. Если пользователь отпускает окно слева от другого, оно вставляется слева; сверху — сверху; в центр — меняется местами. Отдельная команда переводит окно в плавающее состояние. Floating-окно можно двигать и изменять размер обычным способом, но в закреплённом режиме оно всё равно автоматически ограничивается safe-area текущего экрана и не может полностью потеряться за границами. Диалоги, Save As, подтверждения, настройки маленького размера и transient-поверхности автоматически открываются floating над родительским окном и не занимают отдельный tile.

Safe Area должна быть динамической. Верхняя панель всегда учитывается в расчёте рабочего пространства, если пользователь не отключил её резервирование. Правая панель и нижний dock могут либо резервировать место, либо отображаться поверх окон. В выбранной по умолчанию конфигурации, соответствующей макетам, раскрытая правая панель уменьшает доступную ширину tiled-area, а dock уменьшает доступную высоту. Когда панель скрывается, окна плавно расширяются. Когда она появляется, tiled-окна сначала плавно сжимаются и освобождают точное пространство под панель, после чего сама панель въезжает. Поэтому панель никогда не должна внезапно накладываться на исходный код и закрывать полезный интерфейс.

Верхняя панель внешне должна быть почти идентична основному макету. Она состоит из нескольких независимых glass-pill модулей, а не одного сплошного прямоугольника. Слева находится белый логотип Arch и текст `Arch Linux`. Далее отдельная панель с цифрами рабочих зон `1–9`. По центру располагается глобальная строка поиска и команд. Справа — компактная область с громкостью, Wi-Fi, Bluetooth при необходимости, батареей, раскладкой клавиатуры, временем и датой. Все подписи самой оболочки на русском, кроме общеупотребительных имён вроде Arch Linux, Git, Docker и названий приложений.

Центральный поиск открывается через `Super+Space`. В обычном состоянии это короткий glass-pill. После вызова он плавно увеличивается примерно на 15–20 %, фон остального интерфейса при необходимости слегка затемняется, а ниже появляется список результатов. Через него должны искаться приложения, окна, команды, настройки, зоны canvas, bookmarks, серверы, действия shell и файлы из пользовательских индексируемых директорий. Можно набрать «размытие», получить сразу страницу настроек blur; «сервер prod» — увидеть сервер; «GitHub» — открыть сайт; «терминал» — запустить терминал. Escape закрывает поиск без дополнительных подтверждений.

Правая панель должна повторять визуальный принцип изображения: несколько отдельных чёрных стеклянных карточек с одинаковой шириной, скруглением и небольшими gaps. По умолчанию сверху находится «Система»: CPU, ОЗУ, диск, сеть и маленькие графики. Ниже «Серверы»: список машин, latency и статус. Ниже «Задачи». При необходимости пользователь добавляет Git, Docker, медиа, календарь, погоду, сеть, температуры, процессы, VPN, SSH-сессии и собственные widgets. Все блоки можно перетаскивать и изменять по высоте.

Правая панель должна скрываться отдельным bind, например `Super+R`. Карточки уходят вправо за физическую границу монитора. Не просто меняется opacity: выполняется настоящая translation-анимация. Между карточками желательно использовать каскадную задержку около 15–20 мс, чтобы интерфейс ощущался живым, но не декоративно-медленным. Полная длительность около 240 мс. После выхода последнего пикселя экранная поверхность перестаёт принимать mouse input и перестаёт резервировать safe-area. При повторном нажатии сначала layout оставляет место, затем карточки поочерёдно возвращаются. Все параметры этой анимации пользователь может поменять или полностью выключить.

Нижний dock располагается по центру и также выполнен отдельным плавающим glass-pill. На нём находятся только закреплённые пользователем приложения. По умолчанию это терминал, Zed или выбранный IDE, файлы, Zen Browser, Docker/серверный инструмент, GitHub и медиаплеер. Dock не является классической taskbar и не должен автоматически превращаться в список из двадцати окон. Отображение работающего приложения — маленький индикатор либо немного более яркая рамка. Dock скрывается отдельным bind, например `Super+D`. При закрытии он плавно опускается ниже нижней границы монитора, одновременно opacity уменьшается примерно до 0 и scale опционально уменьшается до 0,96–0,98. Возвращение выполняется обратно.

Отдельный `Focus Mode`, например `Super+F`, скрывает dock и правую панель одной общей анимацией, сворачивает ненужные модули top bar, запрещает обычные неважные notification popups и оставляет максимум полезного места под работу. Система должна запоминать, какие панели были открыты до Focus Mode, чтобы после выхода восстановить именно старое состояние, а не просто открыть всё подряд.

Окна оформляются в едином стиле. Базовая рамка неактивного окна — белая около 10–12 % opacity. Активного — примерно 35–45 %. Скругление по умолчанию 12–14 px. Фон окон, которые поддерживают прозрачность, может иметь opacity 0,88–0,96 и blur. Тени должны быть минимальными. Зелёная рамка активного окна запрещена: зелёный в интерфейсе означает success, а не focus. При переходе focus рамка плавно становится ярче примерно за 120 мс.

Эффект жидкого стекла должен оставаться очень сдержанным. Никакого молочного или цветного стекла. Основная поверхность практически чёрная. Glass получается из чёрного полупрозрачного фона, размытия содержимого позади, очень тонкой белой рамки, слабого внутреннего блика по верхней кромке и небольшого noise. По умолчанию карточка может использовать примерно `rgba(0,0,0,0.72)`, border white с opacity 0,14, highlight 0,04 и blur в зависимости от типа элемента. На hover граница становится немного ярче. На press элемент может сжиматься до scale 0,97 примерно на 70–90 мс. Никакого glow вокруг каждой кнопки.

Уведомления интегрируются в правую часть системы. Если основная правая панель видима, popup появляется слева от неё, чтобы панели не пересекались. Если она скрыта, уведомления занимают область справа. Уведомление представляет собой маленькую стеклянную карточку с иконкой или монохромным знаком приложения, заголовком, одной-двумя строками текста, временем и максимум несколькими действиями. Визуальный приоритет должен быть минимальным. Обычное сообщение не окрашивается зелёным. Ошибка получает маленький красный индикатор. Success — маленький зелёный. После заданного времени карточка плавно уезжает вправо и остаётся в истории.

Центр уведомлений открывается отдельным bind. Это вертикальная glass-панель справа, в которой уведомления группируются по приложениям. Для Telegram Web, Discord Web и других мессенджеров необходимо реализовать возможность быстрого ответа, но технически это нельзя обещать для любого сайта только на основании обычного browser notification. Поэтому для поддерживаемых сайтов создаётся companion-extension для Zen Browser и native messaging host. Расширение передаёт shell структурированные сообщения и доступные действия. Если сайт поддерживает наш адаптер, у уведомления появляется поле ответа. Пользователь вводит текст, нажимает Enter, и сообщение отправляется через браузер. Для обычного сайта, где такой интеграции нет, доступны только «Открыть» и системные действия. Благодаря этому интерфейс никогда не показывает кнопку, которая технически не работает.

Zen Browser является рекомендуемым основным браузером и получает собственную тему. Chrome браузера должен быть максимально монохромным и соответствовать оболочке. Слева используются вертикальные вкладки и Spaces: «Разработка», «Серверы», «Учёба», «Общение» и другие пользовательские пространства. Верхняя строка адреса минимальна. Скругления и прозрачности совпадают с системой. Стартовая страница, в отличие от ранее показанного космического пейзажа, в финальной теме должна по умолчанию быть также более минималистичной: чёрный фон, редкие белые точки, центральный поиск, несколько быстрых действий и ничего лишнего. Пользователь может включить более сложный космический вариант отдельно. Интерфейс Zen адаптируется через `userChrome.css`, пользовательский профиль и наше browser-extension. Настройки shell должны уметь изменять только те параметры Zen, которые контролирует наш пакет интеграции.

Системное приложение «Настройки» должно стать фактически визуальным редактором всей рабочей среды. Всё собственное, что существует в shell, backend или fork driftwm, должно иметь настройку в GUI. Нельзя создавать важную функцию, которую пользователь может изменить только вручную в TOML. Сам driftwm всё ещё хранит обычную конфигурацию в `~/.config/driftwm/config.toml` и умеет её проверять через `driftwm --check-config`, поэтому backend должен генерировать корректный config из общей схемы и валидировать его перед применением. ([GitHub][2])

Слева в настройках располагается меню: «Внешний вид», «Цвета», «Рабочий стол», «Верхняя панель», «Боковая панель», «Док», «Уведомления», «Окна», «Тайлинг», «Холст», «Рабочие зоны», «Стекло и размытие», «Анимации», «Шрифты», «Иконки», «Горячие клавиши», «Мышь», «Тачпад», «Клавиатура», «Мониторы», «Виджеты», «Серверы», «Zen Browser», «Экран блокировки», «Экран входа», «Питание», «Автозапуск», «Производительность», «Конфиденциальность», «Резервные копии» и «Расширенные». Сверху находится единый поиск по каждому параметру.

Каждый UI-элемент получает полный набор свойств. Для него можно изменить контейнер, положение, порядок, ширину, высоту, минимальные и максимальные размеры, gap, padding, margin, radius, background opacity, blur, border width, border opacity, shadow, shadow blur, shadow opacity, видимость, условие видимости, auto-hide, reserve-space, слой, animation preset, длительность открытия, закрытия, easing, translation, scale, opacity transition и задержку. Именно так реализуется требование «настроить абсолютно всё», а не через хаотичные отдельные конфиги.

Должен существовать режим «Редактировать интерфейс». После его включения пользователь прямо на рабочем столе видит тонкие рамки вокруг top bar, dock и widgets. Элементы можно перетаскивать. При переносе отображается сетка и snap-линии. Например часы можно переместить слева, системный блок — вниз, workspace switcher — в центр. После перемещения система сама пересчитывает anchors, layout, safe-area и orientation. Нельзя разрешать пользователю визуально поместить элемент в положение, которое приведёт к недоступному интерфейсу; редактор должен контролировать минимальную видимую область и предлагать восстановление.

В разделе анимаций должен быть визуальный редактор. Для каждого события выбирается preset: «Без анимации», «Быстро», «Плавно», «Пружина» или пользовательский. Можно настроить duration, delay, cubic-bezier либо параметры spring, opacity, scale, X/Y translation и blur-transition. Рядом находится live preview. Пользователь нажимает «Проверить», и конкретная карточка воспроизводит анимацию без воздействия на настоящий layout.

Все изменения должны иметь undo/redo. Настройки должны сохраняться атомарно. Backend сначала пишет временную конфигурацию, валидирует её, создаёт snapshot последнего рабочего состояния и только затем активирует. Для опасных параметров — мониторы, input, compositor, shell layers — после применения запускается короткий таймер подтверждения. Если пользователь не подтвердил изменения, автоматически выполняется rollback. Это необходимо, чтобы через GUI было невозможно случайно оставить систему без видимого интерфейса.

Экран блокировки должен соответствовать самому последнему макету и быть значительно минималистичнее ранних вариантов. Он представляет собой тот же абсолютно чёрный фон с редкими белыми точками. В левом верхнем углу маленький логотип Arch и надпись `Arch Linux`. В правом верхнем углу минимальный glass-pill со статусом Wi-Fi, звука, батареи и временем, если пользователь не отключил этот блок. По центру крупное тонкое время, под ним дата. Ниже находится круглый минималистичный аватар или монохромная иконка пользователя и имя аккаунта. Никаких подсказок вроде «Нажмите Enter для разблокировки», «Проведите вверх», «Введите пароль», никаких цитат, приветствий, советов и обучающих элементов на заблокированном состоянии не должно быть. Это личный компьютер, пользователь знает управление.

Когда пользователь начинает печатать или нажимает заранее заданную клавишу, центральный блок плавно изменяется: часы немного смещаются вверх или уменьшаются, а под именем появляется одно минимальное поле пароля. Никакой большой карточки вокруг всего экрана не нужно. Пароль скрывается точками. Enter отправляет пароль, Escape возвращает чистый lock-screen. При неправильном пароле поле на 120–180 мс получает очень тонкую красную рамку и выполняет едва заметное горизонтальное смещение на несколько пикселей. Никаких огромных сообщений «НЕВЕРНЫЙ ПАРОЛЬ». Можно показать короткое «Ошибка» красным текстом на секунду, либо вообще только визуальный feedback — это настраивается.

Блокировка обязана использовать настоящий Wayland session-lock механизм, а не просто fullscreen-окно поверх рабочего стола. Это вопрос безопасности: если shell или locker crash, открытые приложения не должны становиться доступны. Driftwm уже заявляет поддержку session lock, поэтому собственный locker должен работать как отдельный защищённый клиент протокола блокировки и использовать PAM через отдельный минимальный authentication helper. ([GitHub][1]) Пароль нигде не сохраняется, не логируется и не проходит через обычный QML-config.

Экран входа должен выглядеть похоже, но быть отдельным процессом, потому что пользовательская driftwm-сессия ещё не запущена. Рекомендуемая архитектура — `greetd` как session/login backend и собственный минимальный Qt/QML-greeter, запускаемый в маленьком kiosk Wayland compositor вроде Cage. После успешной PAM-аутентификации greetd запускает driftwm-сессию. Сам greeter должен использовать те же design tokens, что и shell и lock screen, чтобы визуально всё ощущалось единой системой.

На экране входа используется только чёрный фон с белыми точками. Слева сверху Arch Linux, справа сверху Wi-Fi, батарея и время. В центре — небольшой аватар, имя пользователя `venhel7`, минимальное поле пароля и кнопка «Войти». Если установлена только одна рабочая сессия driftwm, строку «Сессия: driftwm» вообще можно скрыть. Если сессий несколько, выбор открывается небольшой кнопкой или раскрывающимся элементом. Внизу слева находятся только три иконки без текстовых подсказок: выключение, перезагрузка и сон. При наведении tooltip можно показывать, но его также можно полностью отключить в настройках. Никаких надписей «Нажмите Enter для входа», «Добро пожаловать», «Введите пароль», помощи и инструкции по использованию быть не должно. Поле пароля получает focus сразу после появления экрана, поэтому пользователь просто печатает пароль и нажимает Enter.

Экран входа и lock screen также полностью настраиваются через основную систему после входа. Можно включить или отключить логотип Arch, время, дату, системные индикаторы, аватар, имя пользователя, точки фона, изменить их положение, scale, opacity, radius, blur, отступы и анимации. При этом должны существовать безопасные ограничения: нельзя через GUI убрать абсолютно все способы входа или сделать поле пароля недоступным. Критические элементы authentication могут быть визуально скрыты только в состоянии ожидания, но всегда должны появляться при вводе.

После успешной разблокировки парольное поле растворяется за 100–140 мс, экран блокировки делает opacity transition, а рабочий стол появляется без белой вспышки или промежуточного экрана. После логина из greeter аналогично: фон и точки визуально совпадают по положению настолько, насколько возможно, затем shell появляется поверх них. Благодаря этому вход ощущается как один непрерывный интерфейс.

Backend системы предпочтительно написать на Rust. Он должен отвечать за schema-конфигурацию, layout tree, рабочие зоны, server-monitoring, Git/Docker-адаптеры, browser integration, сохранение состояния и IPC между Quickshell и driftwm. Quickshell/QML отвечает только за визуальную оболочку. Fork driftwm отвечает только за compositor-уровень: Wayland, infinite canvas, Anchored/FreeCanvas, геометрию и анимации окон, session lock и расширенный IPC. Login greeter и lock client — отдельные маленькие процессы. Такое разделение не позволит падению одного компонента разрушить всё окружение.

Quickshell не должен каждые 100 мс запускать `sh`, `grep`, `awk` или `driftwm msg state`. Для driftwm используется постоянный IPC `subscribe`, который сам присылает State при изменениях. CPU и сеть обновляются примерно раз в секунду, RAM можно реже, диски и температуры ещё реже. Если widget скрыт и данные нигде не нужны, частота обновления уменьшается. Это важно для системы, которая должна оставаться лёгкой даже при постоянно запущенной оболочке. Driftwm уже предоставляет такую subscription-модель, включая информацию об окнах, камере, zoom, layout и outputs. ([GitHub][3])

Для нескольких мониторов каждый монитор является отдельным viewport общего canvas, как это уже работает в driftwm. Каждому output соответствует собственная закреплённая рабочая зона, Safe Area и состояние панелей. Переключение Anchored/FreeCanvas выполняется для активного output либо сразу для всех в зависимости от настроек. Правую панель можно привязать к конкретному экрану, dock — к активному либо основному. Рабочие зоны могут хранить раскладку отдельно для разных конфигураций мониторов, чтобы подключение второго монитора не разрушало окна. Driftwm уже рассматривает мониторы как независимые viewport одного canvas, поэтому наша система должна продолжать эту модель, а не пытаться превратить каждый монитор в отдельный классический workspace. ([GitHub][1])

Итоговая система должна восприниматься следующим образом: после включения компьютера пользователь видит почти пустой чёрный экран с редкими белыми точками, маленьким Arch Linux и минимальной формой входа. После авторизации появляется тот же визуальный фон, сверху — тонкие отдельные панели, справа — компактные карточки системы, снизу — небольшой dock. В обычной работе пользователь вообще может забыть о бесконечном canvas: окна ведут себя как строгий красивый tiling WM, открываются внутри экрана и никуда не теряются. Когда нужен infinite canvas, одна клавиша «отстёгивает» текущую область, и driftwm снова становится настоящим свободным пространством. Пользователь перемещается, выбирает другое место и одной клавишей «пристёгивает» экран обратно, после чего новая точка пространства снова становится аккуратным tiling workspace. Правую панель и dock можно мгновенно убрать за края экрана. Весь собственный интерфейс русскоязычный. Любой визуальный или поведенческий параметр проекта можно изменить через единые графические настройки без ручного редактирования конфигов, а настройки, которые могут сломать пользовательскую сессию, защищены preview, валидацией и автоматическим rollback.

Версия спецификации: 1.0

======================================================================
0. ВАЖНОЕ ПРАВИЛО: ЧТО СЧИТАТЬ «ПИКСЕЛЬ-В-ПИКСЕЛЬ»
======================================================================

Все приложенные референсные изображения имеют фактический размер 1672×941 px. Это почти 16:9, но не идеально математически: 1672/941 ≈ 1.777895. Поэтому для точной реализации вводится собственная эталонная система координат 1672×941. Все размеры, координаты, радиусы, отступы, толщины линий и позиции в этом документе считаются каноническими именно для этой системы.

Если интерфейс запускается на другом разрешении, используется коэффициент масштабирования:

S = min(ширина_экрана / 1672, высота_экрана / 941)

После масштабирования:
x_runtime = round(x_ref * S + offsetX)
y_runtime = round(y_ref * S + offsetY)
w_runtime = round(w_ref * S)
h_runtime = round(h_ref * S)

offsetX = (ширина_экрана - 1672*S)/2
offsetY = (высота_экрана - 941*S)/2

Для 1920×1080 предпочтительно масштабироваться по высоте:
S = 1080 / 941 ≈ 1.1477152.
Ширина эталонной сцены станет ≈1918.98 px, поэтому остаток ≈1.02 px делится слева и справа. На практике: offsetX ≈0.5 px.

Если требуется именно идентичный пиксельный скриншот, тестовый Preview обязан запускаться ровно в 1672×941 при scale 100%. На других разрешениях совпадение должно быть геометрически пропорциональным, но из-за rasterization шрифтов и округления отдельных размеров абсолютное совпадение по каждому физическому пикселю невозможно без предварительного рендеринга в 1672×941 с последующим масштабированием всей сцены одним transform.

Для Windows Preview и Arch Production необходимо использовать один и тот же:
- шрифт;
- набор иконок;
- значения цветов;
- порядок слоёв;
- easing-функции;
- длительности;
- logical size;
- QML-компоненты.

Отдельная Windows-реализация тех же элементов запрещена. Windows Preview должен использовать те же QML-компоненты, которые позже будут подключены к Quickshell.

======================================================================
1. ОБЩАЯ ВИЗУАЛЬНАЯ КОНЦЕПЦИЯ
======================================================================

Система должна выглядеть максимально минималистично, холодно, технологично и спокойно. Это не яркий «gaming desktop», не цветная cyberpunk-тема и не классический Linux rice с десятками декоративных элементов. Главная эстетика — почти полностью чёрная поверхность, редкие белые светящиеся точки, тёмное стекло, тонкие полупрозрачные белые контуры и очень небольшое количество зелёного/красного, используемого только как смысловой статус.

Система должна визуально восприниматься так, будто все панели и окна лежат на одном чёрном глубоком фоне и состоят из одного семейства материалов. Не допускается ситуация, когда top bar имеет один blur, dock другой радиус, окно третий border, а настройки четвёртый стиль.

Главные принципы:
1. Чёрный — основа.
2. Белый — интерфейс, типографика, контуры, иконки.
3. Зелёный — только положительный статус.
4. Красный — только ошибка/критический статус.
5. Любой «серый» получается прозрачностью белого/чёрного, а не отдельным цветом.
6. Синий, жёлтый, фиолетовый и другие цвета не используются самой оболочкой.
7. Сторонние приложения и содержимое сайтов не перекрашиваются насильно.
8. В декоративных элементах нет ярких градиентов.
9. Анимации короткие и функциональные.
10. Интерфейс не должен давать подсказки там, где пользователь и так знает действие.
11. Никаких обучающих надписей на lock screen/login.
12. Любое свободное пространство считается частью дизайна и не должно заполняться элементами «просто чтобы не пустовало».

36. ЧТО НЕ ТАК С РЕФЕРЕНСАМИ И КАК ЭТО ИСПРАВИТЬ В ФИНАЛЕ
======================================================================

Референсы красивы, но для постоянной работы имеют потенциальные проблемы.

1. Правая колонка занимает значительную ширину.
Решение: обязательное скрытие bind + Focus Mode.

2. Dock визуально хорош, но при постоянном reserve отнимает вертикаль.
Решение: auto-hide и overlay/reserve режим.

3. Quote в top-right создаёт атмосферу, но добавляет noise.
Решение: default off в рабочем профиле, on только cosmetic profile.

4. В browser reference встречаются синие/жёлтые цвета внутри сайтов.
Это не нарушение системной 4-color palette, так как это content.

5. Settings screenshot содержит много controls одновременно.
Решение: секции/поиск, но размеры оставлять компактными.

6. Blur может сильно нагрузить слабый GPU.
Решение: performance profile снижает blur и отключает backdrop animation.

7. Звёзды должны быть редкими.
Если их слишком много, интерфейс превращается в тематический wallpaper, а не минимализм.

39. ИТОГОВОЕ ОЩУЩЕНИЕ
======================================================================

Интерфейс должен ощущаться не как «набор Linux-виджетов», а как одна цельная система. Пользователь видит чёрное пространство, тонкие белые стеклянные поверхности и почти не замечает shell до тех пор, пока она не нужна. В обычном Anchored режиме окна аккуратно укладываются в доступную область, не теряются на canvas и не перекрываются панелями. Правая колонка и dock присутствуют только когда полезны, а по бинду мягко уходят за край. Focus Mode освобождает максимум пространства. FreeCanvas сохраняет уникальность driftwm, но не мешает повседневной работе. Lock и login продолжают тот же визуальный язык, но ещё сильнее минимизированы. Любая настройка меняется через единое приложение, а не через ручное редактирование десятка несвязанных конфигов.

Эта спецификация должна считаться эталонной. Если текущий референс и значение из спецификации расходятся на 1–3 px, при реализации следует ориентироваться на спецификацию, потому что именно она превращает изображение-концепт в детерминированный UI, который можно одинаково воспроизвести на Windows Preview и на Arch.

40. НОРМАТИВНОСТЬ И РАЗРЕШЕНИЕ ПРОТИВОРЕЧИЙ

Эта редакция фиксирует окончательные решения там, где раннее функциональное ТЗ, pixel-spec и изображения расходятся. Приоритет: безопасность -> механика Anchored/FreeCanvas -> реальные ограничения Wayland/driftwm/Quickshell -> design tokens -> геометрия спецификации -> художественные детали референса.

Конкретные решения:
- На lock-screen референсе есть цитата, но production-профиль её не показывает. Цитата остаётся необязательным модулем.
- На login-референсе есть «Сеанс: driftwm». Если установлена ровно одна сессия, selector скрыт. При двух и более — показывается.
- Собственная оболочка русская. Английский контент сайтов не переводится принудительно.
- Синие, жёлтые, оранжевые и иные цвета допустимы только внутри стороннего содержимого; системные поверхности, focus, status и shell-owned controls остаются в 4-цветной логике.
- Верхняя декоративная цитата desktop optional и по умолчанию выключена в профиле «Работа».
- «Пиксель-в-пиксель» строго проверяется на 1672×941, scale 100%, с фиксированными версиями шрифтов/иконок. На других DPI допускается только пропорциональная эквивалентность.

41. СОСТАВ ПРОЕКТА И ГРАНИЦЫ ОТВЕТСТВЕННОСТИ

41.1 driftwm-fork отвечает только за compositor-уровень: Wayland, infinite canvas, camera/zoom, output geometry, положение surface/window в canvas, focus/stacking, screen-pinned/layer-shell surfaces, window interpolation, Anchored/FreeCanvas runtime-state, запрет pan/zoom, session-lock protocol и расширенный IPC.

41.2 shell-core — отдельный daemon, предпочтительно Rust. Он является авторитетным источником конфигурации, рабочих зон, tiling tree, Safe Area, правил размещения окон, состояний panel/dock/focus, системных интеграций, server monitoring, notification bridge, browser bridge, persistence, миграций и rollback.

41.3 shell-ui — Quickshell + Qt/QML. Он только отображает состояние и отправляет команды. В QML нельзя хранить авторитетное layout-state, самостоятельно редактировать config.toml и опрашивать систему через постоянные shell-команды.

41.4 shell-lock — отдельный защищённый Wayland session-lock клиент. Обычный shell-ui не используется как security boundary.

41.5 auth-helper — минимальный helper для PAM. Пароль не передаётся через обычный config/лог/telemetry.

41.6 shell-greeter — отдельный Qt/QML greeter для greetd, запускаемый до пользовательской сессии и использующий readonly theme snapshot.

41.7 zen-integration — userChrome.css, optional userContent.css, extension, native messaging host, version compatibility layer и rollback.

41.8 windows-preview — отдельный Qt/QML executable на Windows, который использует те же QML-компоненты, Theme tokens и motion presets. Отличается только backend: MockBackend вместо Linux services.

43. ЕДИНАЯ МОДЕЛЬ СОСТОЯНИЯ

OutputState должен содержать: outputId, stable fingerprint, logicalRect, scale, transform, refreshRate, activeZoneId, cameraX/Y, zoom, mode Anchored|FreeCanvas, topBarState, rightPanelState, dockState, focusMode, fullscreenPolicy, safeArea, lastPointerPosition, lastFocusedWindowId.

Title запрещено использовать как единственный identity. Приоритет: app_id -> role/metadata -> XWayland class/instance -> title regex как last resort.

44. STATE MACHINE ANCHORED/FREECANVAS

Состояния:
AnchoredStable -> ReleasingAnchor -> FreeCanvasStable -> SearchingSnapTarget -> SnappingToExistingZone | CreatingNewZone -> RestoringTiling -> AnchoredStable.
Отдельное ErrorRecovery.

AnchoredStable:
- pan hard-disabled;
- zoom hard-disabled;
- ordinary windows tiled;
- Safe Area authoritative;
- camera хранит точные координаты зоны.

toggle-anchor из AnchoredStable:
- начинается короткий release transition;
- geometry окон не меняется;
- camera unlock выполняется только в конце;
- повторный conflicting trigger не должен создавать второе состояние; он либо reverse, либо игнорируется согласно motion policy.

В FreeCanvasStable camera свободна. Повторный toggle выполняет поиск существующей зоны.

Snap candidate определяется в screen-space. Default threshold = 0.35 диагонали viewport. Zoom tolerance default ±12%. Если кандидатов несколько, используется score distance+zoomPenalty. Hysteresis 10% предотвращает прыжки между двумя зонами.

Existing zone:
- camera и zoom плавно интерполируются к сохранённым значениям 280 ms;
- hard lock включается после завершения;
- затем пересчитываются Safe Area и layout.

New zone:
- фиксируется текущая camera;
- создаётся UUID;
- quickSlot не присваивается автоматически, если все 1..9 заняты;
- найденные окна обрабатываются выбранной policy;
- default: не захватывать случайные окна;
- затем включается Anchored.

Любая ошибка transition должна rollback в последнее стабильное AnchoredStable или FreeCanvasStable состояние.

45. TILING ENGINE

Layout хранить деревом:
SplitNode(horizontal|vertical, ratio, childA, childB)
StackNode(children, activeIndex)
LeafNode(windowId)
PlaceholderNode(rule/empty)

Ratio default min/max 0.15..0.85 с учётом min-size.
Master Stack default masterRatio=0.58, masterCount=1.
Grid: cols=ceil(sqrt(N)), последняя строка по policy stretch|center.
Columns/Rows сохраняют user ratios.
Monocle: все targetRect одинаковые, active leaf визуально сверху.

Новый обычный window в Anchored: app-rule -> transient check -> restore match -> insertion policy.
Insertion: after-focused | master | end-of-stack | nearest-empty.

46. FLOATING, TRANSIENT, PIP, FULLSCREEN

Floating окно обязано сохранять минимум 48×24 px drag-accessible area внутри Safe Area. LastFloatingRect хранится отдельно от tile path.

Transient/dialog:
- не входит в tiling tree;
- центрируется относительно parent;
- всегда above parent;
- clamp до usable output при чрезмерном размере.

Picture-in-Picture:
- floating;
- default top-right внутри Safe Area;
- не tile;
- может быть pinned across zones только по явной настройке.

Fullscreen:
- target полный logical output;
- shell panels по fullscreenPolicy;
- при выходе восстанавливается предыдущий tiled/floating state;
- FocusMode snapshot не теряется.

Urgent window не крадёт focus по default; zone/workspace indicator получает маленький красный semantic marker.

47. SAFE AREA — ЕДИНСТВЕННЫЙ ВЛАДЕЛЕЦ

Итоговую Safe Area рассчитывает только shell-core. Нельзя позволить RightPanel, Dock и tiling независимо вычитать размеры.

SafeArea = OutputLogicalRect - TopReserved - BottomReserved - LeftReserved - RightReserved - UserOuterMargin.

Surface states передают desired reserve. shell-core рассчитывает итог и одной layout revision обновляет окна.

Открытие panel в reserve-mode:
1) выставить target reserved space;
2) рассчитать window targets;
3) начать reflow;
4) на 55–65% reflow начать въезд panel;
5) обе анимации завершаются согласованно.

Закрытие:
1) panel начинает exit;
2) reserve сохраняется до безопасной точки;
3) reserve идёт к 0;
4) окна расширяются;
5) input region panel становится empty только после выхода.

Если Safe Area слишком мала:
1) скрыть optional widgets;
2) RightPanel перевести overlay;
3) Dock auto-hide/overlay;
4) layout -> Monocle.
Нельзя сжимать tiled окна ниже usability limits.

48. INTERRUPTIBLE MOTION

Любая show/hide/layout/camera animation должна быть прерываемой. При reverse новый transition стартует с текущего visual value, а не с endpoint. Remaining duration рассчитывается пропорционально оставшейся дистанции.

Смена зоны во время camera transition меняет target без teleport. Желательно сохранить velocity либо мягко её погасить.

Blur radius не анимировать каждый frame; анимируются transform/opacity/border.

49. PANEL STATE MACHINE

Hidden, Showing, Visible, Hiding.
Visible: input active, reserve согласно policy.
Hidden: input region empty, reserve=0 для hidden state.
Show во время Hiding и Hide во время Showing — reverse current transition.

System pill: audio, Wi-Fi, optional Bluetooth, battery if exists, layout, clock/date.
Если battery device отсутствует — блок скрывается, а не показывает фиктивные 100%.

Network: connection, signal, known networks, VPN.
Bluetooth: power, paired devices, connect/disconnect.

Browser extension -> native messaging host -> shell-core.
Каждый adapter: origin allowlist, schemaVersion, conversationId, messageId, capabilities, sendReply.
Любая browser payload валидируется; строка из браузера никогда не исполняется как shell command.

Domains:
1 shell commands;
2 settings;
3 .desktop apps;
4 open windows;
5 zones;
6 bookmarks;
7 explicit local index roots;
8 servers;
9 browser shortcuts.

Не индексировать весь HOME без разрешения.

56. RIGHT PANEL WIDGET API

Widget manifest: id, version, title, icon, minWidth, minHeight, preferredHeight, updatePolicy, settingsSchema, capabilities, privileges, singleton, resizable.

Default — локальный список shell. Никаких вымышленных задач, если источник не настроен.

userChrome.css version-pinned. При обновлении Zen выполнять compatibility check. Если версия несовместима, не применять ломающий CSS; browser должен оставаться usable.

Theme package: expected Zen version range, CSS hash, extension version, rollback snapshot.
Нельзя обещать перекраску arbitrary web content. Системная тема контролирует browser chrome и нашу new-tab page.

schemaVersion обязателен.
Migration chain N->N+1.
Перед миграцией backup.
Не менять старый файл in-place до успешной проверки.
Migration fail -> safe mode, user data preserved.
Unknown fields желательно сохранять при round-trip.

Runtime state и user settings раздельны.
Сохранять zones, panel visibility, active zone per output, layout ratios, floating rects, last focus.
Процессы сторонних приложений не эмулировать самостоятельно; использовать нормальные launch/session restore mechanisms.

shell-ui.service

67. ACCESSIBILITY

Reduced Motion: durations <=80 ms, no scale/stagger, короткий camera transition.
High Contrast optional: повышать alpha, не вводить новые colors.
Декоративные stars исключены из accessibility tree.

68. INPUT

Anchored блокирует canvas pan/zoom gestures, но не scroll внутри приложений.

70. MULTI-MONITOR / DPI

Вся геометрия runtime — logical px. Physical px только golden test.
Fractional scale поддерживается.
Rotation учитывается до Safe Area.
Hotplug debounce 300–500 ms.
Output fingerprint хранит профиль.
Unplug активного output не должен потерять окна: выбрать fallback, обеспечить reachability, затем re-anchor по policy.
Mixed refresh rates: motion time-based, не frame-count-based.

71. PERFORMANCE BUDGET

Цели при idle:
shell-core CPU <0.5% одного современного ядра в среднем;
shell-ui CPU <1% при статичном screen;
core RSS target <80 MiB;
UI RSS target <180 MiB без тяжёлых third-party widgets.
CPU/network sampling ~1s; memory ~2s; disk/temp 5–10s.
Animation target минимум 60 FPS, не искусственно ограничивать 120/144 Hz.
60 Hz frame budget 16.67 ms, shell render желательно <8 ms.

72. POWER-AWARE MODE

Battery saver: blur quality ниже, hidden widgets pause, metric intervals реже, decorative animation off, stars static. Функциональность не отключается.

74. ОБЯЗАТЕЛЬНЫЕ EDGE-CASE TESTS

Ни один сценарий не должен оставлять окно полностью недоступным.

75. ARCH PACKAGING

PKGBUILD/пакеты устанавливают binaries, assets, systemd user units, schemas и defaults в /usr/share/<project>. User config создаётся в ~/.config при первом запуске. Update не перезаписывает пользовательский config без backup и не требует ручного копирования QML.

76. FIRST RUN

Нет onboarding, подсказок и wizard по умолчанию. Создать безопасный default config и рабочий профиль. При недостающем optional subsystem — Diagnostics warning, не навязчивый popup.

77. ВИЗУАЛЬНЫЕ ПРОФИЛИ

Work default: right panel visible, quote off, dock according preference, blur medium, sparse stars.
Focus: right+dock hidden, DND, top compact.
Minimal: минимум shell modules, low blur.
Showcase: decorative quote/effects allowed, но не default.

78. «АБСОЛЮТНО ВСЁ НАСТРАИВАЕТСЯ» — ТОЧНОЕ ОПРЕДЕЛЕНИЕ

Любой безопасно изменяемый public parameter собственной оболочки и fork имеет schema + GUI. Это не означает возможность удалить security invariants, навсегда спрятать password path, создать отрицательную геометрию, выдавать root commands или лишить пользователя аварийного доступа к Settings.

79. DEFINITION OF DONE

Готовность означает одновременно:
- стабильный Anchored/FreeCanvas без config reload;
- tiling 1..N и корректные transient/floating/fullscreen;
- зоны persist/restore;
- TopBar/RightPanel/Dock/Focus функциональны;
- Search работает по заявленным источникам;
- notifications/history/actions корректны;
- quick reply capability-driven;
- Settings покрывает public settings;
- Design Mode безопасен;
- lock настоящий session-lock;
- greeter реальная PAM/greetd auth;
- Zen theme rollback;
- multi-monitor не теряет окна;
- safe mode, migration, rollback работают;
- golden screenshots проходят;
- secrets не логируются;
- production UI русский;
- 4-color semantics соблюдаются.

80. ФИНАЛЬНЫЙ КОНТРАКТ

В обычной работе система ощущается как строгий tiling desktop. Infinite canvas не мешает, но доступен одной клавишей. Повторное закрепление превращает текущую camera position в безопасную tiling-zone. RightPanel и Dock физически уходят за экран. Reserve-mode не закрывает код. Focus освобождает максимум площади. Shell остаётся почти полностью чёрно-белым; green/red используются только как semantic status. Lock/login без подсказок. Любая risky настройка имеет rollback, любая integration — graceful degradation, любая анимация — interruptible, каждый основной экран — golden reference.
